# ADR-0010 · 在线升级：升级只下应用本身，建模引擎是一个独立版本的组件

状态：已采纳（2026-09-21）。**应用侧已实现并在本机验证；发版流水线的新增步骤和真实的下载地址还没有被真实运行验证过**（见文末「要负责人做的两件事」）。

## 背景

安装包 232 MB，其中 224 MB 是建模引擎（内嵌 CPython + build123d + OpenCascade），应用本身只有十几 MB。引擎很少变（到现在只有一个版本 `b123d-0.12.0-py312-1`），应用几乎每天在变。如果在线升级照搬「下载新的安装包、装上」，每次升级都要重新下这 224 MB——而里面的东西和用户机器上已经解开的那一份一模一样。

试过从压缩上想办法，没有用：整个安装包再用 LZMA2 极限压缩一遍是原来的 99.99%；引擎包换成 zstd 最高档只小 2.5%。要省的不是压缩率，是**别重复下载没变的东西**。

## 决定

**1. 两种产物，各管各的事。**

| 产物 | 给谁用 | 内容 | 大小 |
|------|--------|------|------|
| 完整安装包（`…-setup.exe` / `.dmg`） | 第一次安装 | 应用 + 引擎包 | 约 232 MB |
| 精简升级包（`…-update.exe` / `.app.tar.gz`）+ 签名 | 应用内升级 | 只有应用；引擎那个目录里只留一份清单 `cad-engine.json` | 十几 MB |

「单个安装包、用户零安装、首次使用不联网」这条硬约束不变——那是完整安装包的事。升级走精简包。

**2. 引擎是一个独立版本的组件。** 它本来就解在应用数据目录里、带着自己的版本号（`cad-engine/python/engine.json`），应用升级不动它。应用每次启动看的是清单：

- 解开的引擎版本 = 清单要的版本 → 什么都不做（**绝大多数升级都是这种**）；
- 版本不对、安装目录里带着包 → 从包里解（完整安装包的首次使用，不联网）；
- 版本不对、安装目录里**没带包** → 这一版换了引擎，而用户是走精简包升上来的 → 按清单里的地址**单独下载引擎包**（同一个引擎版本只下这一次），校验 SHA-256，之后和自带的包走同一条路（解到临时目录、原子换名）。几百 MB，所以界面先问一句、用户点了才下，不自动开始。
- 安装目录里的包和清单对不上（精简包覆盖安装之后留下了上一版的包）→ 按大小识别出来，当作没带，走下载。

引擎包发到一个单独的 Release（`engine-<引擎版本>`），同一个引擎版本只传一次；应用的每次发版不再重复带它。

**3. 升级机制照搬 velo：`tauri-plugin-updater`。** 清单地址和验签公钥在 `tauri.conf.json` 的 `plugins.updater` 里。下载到的包由插件按公钥验签，验不过不会安装。Windows 用 `passive` 安装模式（有进度、不用点下一步），装完应用自己重启。

- 启动 6 秒后静默查一次：查不到（断网、地址还没配好）什么都不说；有新版本才提示一句。「设置 → 软件更新」里可以手动查、看更新说明、下载并安装（带进度）。
- 公钥沿用 velo 的那一把（PRD 第 9 节的约定：沿用 velo 的签名与发布流水线）——负责人手里已经有对应的私钥，不需要再生成、保管一把新的。想分开的话，换掉 `pubkey` 和仓库密钥即可。
- 清单地址有两个，按顺序试：`https://dl.zotrus.com/printpilot/latest.json`（仿照 velo 的 `dl.zotrus.com/ztmail/latest.json`）和 GitHub Release 上的 `latest.json`。

**4. 发版流水线只做加法。** 原来出完整安装包的步骤一个字没动。新增的步骤（给清单写下载地址、发布引擎包、打精简包并签名、拼 `latest.json`）**只有配了签名私钥才执行**，而且全部 `continue-on-error`——它们失败不会拦住正常发版。精简包的做法是把引擎包暂时挪开、用同一份已编译的产物重新打一次包（`createUpdaterArtifacts` 只在这一次打开），不重新编译。

## 为什么不用别的办法

- **二进制增量补丁**（bsdiff、zstd `--patch-from`）：Tauri 的升级插件不支持；要自己管补丁链、回退、校验。而「应用 / 引擎」这条天然的分界线已经拿到了绝大部分收益：升级从 232 MB 降到十几 MB。
- **引擎完全不进安装包、首次使用时下载**：违反「首次使用不联网」，国内网络下几百 MB 的首次下载也是最容易把新用户劝退的一步。
- **把引擎包压得更狠**：实测 zstd 最高档只小 2.5%，换 LZMA 也就一成多，还得给应用加一个新的解码器。另外应用用的 `ruzstd` 解码器最多支持 100 MiB 的窗口——引擎包的 zstd 窗口不能超过 2^26，否则用户机器上解不开。

## 要负责人做的两件事（做之前，应用里的「检查更新」只会说「检查更新失败」，别的都不受影响）

1. **把签名私钥放进仓库密钥**：`TAURI_SIGNING_PRIVATE_KEY`（和 velo 用的是同一把）以及 `TAURI_SIGNING_PRIVATE_KEY_PASSWORD`。没有它们，流水线不会出精简包和 `latest.json`——发版照常，只是没有可供升级的东西。
2. **让更新清单和升级包能被匿名下载**。仓库是私有的，Release 附件匿名下载不了，所以二选一：
   - 把 `latest.json`、各平台的 `…-update.*`（及 `.sig`）、引擎包同步到 `dl.zotrus.com/printpilot/`（和 velo 一样的做法），并把仓库变量 `UPDATE_DOWNLOAD_BASE` 设成那个目录的地址——`latest.json` 里的下载地址就会指向那里；或者
   - 把仓库（或者另建一个只放发布物的公开仓库）公开，什么都不用设。

## 验证到哪一步

- 已验证：下载器（落盘是原子的、半截断开和 404 不留文件、明文外部地址不下，本机 HTTP 服务测试）；「带没带引擎包」的判断（只有清单 / 留着旧包 / 完整包）；`release-tools.py` 的两个子命令；流水线 YAML 能解析、原有步骤顺序没变；应用在没有可用更新地址时的表现（启动静默、手动检查给出一句话）。
- **没法在本机验证的**：流水线新增的那几步（要有密钥、要真的跑一次 Actions）；从真实地址检查 / 下载 / 验签 / 安装这一整段（要先有第 2 件事里的下载地址）；macOS 上的升级。第一次带着密钥发版之后，要从上一个版本实际升一次，才算数。
